# Sohan Soft Tech: custom domains and subscription billing

The permanent platform URL is https://erp.sohansoft.in. Institution subscriptions are paid to Sohan Soft Tech's merchant accounts. Each institution's existing student-fee gateway remains independent.

## 1. One-time Cloudflare setup (platform owner)

1. In Cloudflare, open the **sohansoft.in** zone. Enable **SSL/TLS → Custom Hostnames → Cloudflare for SaaS**. If Cloudflare requests product activation or billing approval, complete it in your account.
2. Copy the zone's **Zone ID** from its overview (32 hexadecimal characters).
3. Create an API token with **Zone → SSL and Certificates → Edit**, restricted to **sohansoft.in**. The application does not need a global API key, account-wide token, DNS edit permission or Worker edit permission for hostname provisioning.
4. In the ERP, open **Platform Settings → Custom domains**, enter the Zone ID and token. They are encrypted on the server. Environment-variable configuration remains a fallback; it is no longer the only way to connect Cloudflare.
5. Deploy the small **domain proxy Worker** included in `/setup/sohan-domain-proxy.zip` in your Cloudflare account. This forwards customer-domain traffic to the existing ERP and signs the original hostname so the backend can securely choose its institution.
   - Unzip the package in a local folder.
   - Run `npx wrangler login` with your own Cloudflare account.
   - Run `npx wrangler secret put DOMAIN_PROXY_SECRET --config wrangler.json`. Enter a randomly generated secret of at least 32 characters. Do not put it in source files or share it in chat.
   - Run `npx wrangler deploy --config wrangler.json`.
   - Enter the **same secret** in ERP **Platform Settings → Domain proxy shared secret**.
   - Worker deployment requires permission to deploy Workers; that is separate from the limited hostname API token stored in the ERP.
6. In the sohansoft.in zone, add a **proxied** originless DNS record:

   | Type | Name | Value | Proxy |
   |---|---|---|---|
   | AAAA | saas-origin | 100:: | Proxied |

   Select **saas-origin.sohansoft.in** as the Cloudflare for SaaS **fallback origin**.
7. Under **Workers Routes**, add the route `*/*` to `sohan-erp-domain-proxy`. BEFORE enabling it, create more-specific **No Worker / None** exclusions for `erp.sohansoft.in/*`, `sohansoft.in/*`, `www.sohansoft.in/*` and every other existing company hostname that must retain its current origin. Keep the existing ERP DNS target, and ensure the erp.sohansoft.in record is **Proxied / orange cloud** so customer CNAME traffic enters this SaaS zone. These exclusions prevent recursion and preserve your company website.
8. In ERP Platform Settings, click **Check Cloudflare connection**. The fallback status must be active. This checks API access and fallback configuration; actual end-to-end routing must be checked on a customer domain after DNS/SSL activation.

Cloudflare reference: https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/advanced-settings/worker-as-origin/

## 2. Map an institution domain

1. Open **Institutions → institution → Domain**.
2. Save a hostname such as `fees.school-example.in` (use a subdomain for the simplest setup).
3. Click **Provision / Check Cloudflare**.
4. Ask the customer to create:

   | Type | Name in customer DNS | Target |
   |---|---|---|
   | CNAME | fees | erp.sohansoft.in |
   | TXT | Exact ownership/SSL record name displayed by Cloudflare | Exact displayed token |

   Initially use DNS-only for the customer's CNAME. Follow Cloudflare's O2O documentation before enabling a customer-side proxy.
5. Copy **all** displayed TXT records exactly, without changing names or values. Ownership TXT and certificate TXT may be different. The CNAME target stays `erp.sohansoft.in`; TXT names/values are generated by Cloudflare and cannot all be that hostname.
6. If TXT records are pending, refresh **Check Cloudflare** later. Initial hostname creation may not yet contain SSL validation records. No invented token or false Verified status is shown.
7. Wait for ownership, SSL and hostname statuses to become active, then test login, navigation and an ordinary tenant operation through the custom hostname.

Common errors: wrong Zone ID; token missing the zone-specific SSL permission; SaaS not enabled; inactive fallback; proxy Worker/shared secret missing; incorrect CNAME; TXT copied into the wrong DNS zone; CAA blocking issuance. Apex domains require separately supported flattening/apex proxying; a subdomain avoids that extra setup.

Reference: https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/create-custom-hostnames/

## 3. Razorpay subscription payments

1. Register/activate your Sohan Soft Tech merchant account, complete business KYC and bank verification. Submit `https://erp.sohansoft.in` as the website where customers will purchase ERP subscriptions. Provide accessible business contact, pricing, terms, privacy and cancellation/refund information as requested during merchant review. Do not submit an institution's student-fee merchant account for platform billing.
2. Start in **Test Mode**. In **Account & Settings → Website and app settings → API Keys**, generate the **Key ID** and **Key Secret**.
3. In ERP **Platform Settings → Subscription payment gateways → Razorpay**, enter the test keys, select Test and enable Razorpay.
4. In Razorpay **Account & Settings → Webhooks**, add the URL below and select **payment.captured**. Choose a webhook secret and enter the identical value in ERP's **Razorpay webhook secret** field. The webhook secret is separate from the merchant Key Secret.
5. Configure automatic payment capture. A merely authorized payment does not activate a subscription.
6. Complete a sandbox purchase and verify the ERP order, subscription dates and payment history. For production, finish merchant/website approval, generate Live keys, switch ERP to Production and save matching Live-mode webhook configuration. Do not rotate keys while an order is pending unless you arrange reconciliation first.

API-key reference: https://razorpay.com/docs/payments/dashboard/account-settings/api-keys/
Standard Checkout reference: https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/

## 4. Cashfree subscription payments

1. Activate your Sohan Soft Tech **Payment Gateway** merchant account and complete business/KYC/bank and website review. Submit/whitelist `https://erp.sohansoft.in` for hosted checkout. Follow the website approval/domain settings available in your merchant account; if approval is blocked, contact Cashfree merchant support.
2. In **Payment Gateway Dashboard → Developers → API Keys**, generate sandbox **App ID** and **Secret Key**. Use Payment Gateway credentials, not Payouts credentials.
3. In ERP **Platform Settings → Subscription payment gateways → Cashfree**, enter them, select Test and enable Cashfree. No separate Cashfree webhook secret is needed: verification uses the Payment Gateway client secret.
4. In **Payment Gateway → Developers → Webhooks**, add the URL below, choose webhook version **2025-01-01**, and enable **Success Payment** (`PAYMENT_SUCCESS_WEBHOOK`).
5. Provider callbacks must preserve the raw request body, `x-webhook-timestamp` and `x-webhook-signature`. Unsigned probes never activate subscriptions. Valid signed test events for unknown orders are acknowledged without inserting payment records. Use a real sandbox checkout to test actual settlement.
6. Save a valid institution mobile number in its settings (Cashfree requires an Indian customer phone number).
7. After successful testing and account approval, generate Production keys with the required 2FA, switch ERP to Production, and configure the Production webhook. A sandbox success does not move real funds.

References:
- https://www.cashfree.com/docs/api-reference/authentication
- https://www.cashfree.com/docs/payments/online/webhooks/configure
- https://www.cashfree.com/docs/payments/online/webhooks/signature-verification

## 6. Customer dashboard and verification

- Create an active paid plan in **Platform → Plans**. Free plans are not displayed for online purchase.
- Institution admins see **Subscription & billing** in their own navigation. Accountants, teachers and platform support sessions cannot purchase.
- In Test mode, checkout is hidden and blocked for institutions outside the configured **Allowed test institution codes**. Defaults are CL-TEST and GV-TEST. Add another confirmed test code explicitly when needed. Production mode is used for ordinary paying customers.
- Either enabled gateway, or both, can be available. Customers using custom domains are directed to the canonical ERP billing portal for checkout on the merchant-approved domain.
- The plan price and usage limits are authoritative on the server. Retries share a durable idempotency key. A pending order must be resumed/checked before another purchase.
- **Check payment** makes a read-only provider query; it does not create a second charge.
- A verified captured payment atomically records a subscription payment, two balanced immutable postings, subscription limits/dates and the audit entry. Student fee ledgers remain independent.
- Same-plan renewal extends the current term without interrupting access. Changing plans starts a new full-price term today; unused time is not prorated. These are manual purchases/renewals, not automatic-debit mandates. Automatic recurring mandates require a separate product integration and provider approval.
- If an administrator changes a subscription while checkout is pending, automatic settlement stops with a review error. Compare the merchant transaction with the pending order and contact platform support; the callback does not overwrite supervisor settings. A lost Razorpay order-creation response may also require merchant-dashboard reconciliation before another purchase.

## 7. Institution cleanup and permanent deletion

No institutions were deleted during this upgrade. CL-TEST and GV-TEST are confirmed test tenants. GCITY-123, ASDASD, CSA-ADMY and CSA require the owner to decide whether they are unwanted; names, status or seed history are not proof that they are safe to remove.

Existing deletion workflow remains permission-gated: exact institution name, second warning, fresh six-digit Super Admin OTP (five-minute expiry, five attempts), encrypted verified backup, seven-day quarantine, fresh OTP recovery/finalization, resumable batches and immutable audit records. Financial records and required ancestors are retained with an inaccessible Deleted tombstone. Operational tenant data/domains are purged consistently after the recovery window. Recovery after final purge is an operator process using an isolated backup restoration, not an automatic public restore.

Granular platform roles continue to govern institutions, domains, reports, users, payment configuration and deletion on both UI and server. No cleanup proceeds without explicit confirmation of the exact institution codes.
