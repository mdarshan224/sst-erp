# Financial core and tenant routing

The existing fee engine already posts immutable `ledger_entries` atomically with invoice/payment/refund operations. A database trigger creates one `journal_events` transfer per source entry. Each transfer yields exactly two `journal_postings` rows with equal integer-paise debits and credits. Fee balances remain derived from append-only financial records; payment-processing and fee-configuration statuses are operational metadata, not financial authority.

`db/schema.ts` now exports typed financial event and account-code unions, including INVOICE_GENERATED, PAYMENT_RECEIVED, CONCESSION_APPLIED and REVERSAL_ISSUED. Late fees, adjustments and academic-year transfers remain supported. Drizzle also rejects UPDATE/DELETE against ledger and journal tables before execution; existing database immutability and tenant triggers remain authoritative for raw SQL.

Migration `0009_ordinary_talos.sql` is additive: it adds `(institution_id, academic_year_id, event_type, created_at)` on journal events and ensures the three requested existing indexes are present without creating duplicate indexes. Fees use `fee_structures(institution_id, academic_year_id, status)`, payments use `(institution_id, student_id, created_at DESC)`, and roll numbers use `enrollments(institution_id, roll_number)`. Roll numbers belong to year-specific enrollments; duplicating them on students would compromise academic-year history.

The migration adds source-provenance validation for journal inserts. Historical ledger entries are exposed through `journal_effective_events` until their corresponding journal event is materialized by the existing bounded idempotent backfill. `journal_postings` therefore includes the complete historical double-entry representation immediately and never duplicates rows when backfill runs. No old ledger, payment or invoice record is rewritten, and no full-table data backfill runs during deployment.

`server/tenancy.ts` exports `institutionMiddleware`: authenticated membership → permission guard → subscription policy → AsyncLocalStorage tenant scope. `tenantDatabase(actor)` additionally requires the current institution and user to match the actor. `server/queries.ts` uses this accessor for Drizzle reads. `db/index.ts` injects institution IDs on inserts and combines tenant predicates with SELECT/UPDATE/DELETE filters. It exposes no raw builder, global-table query or replaceable WHERE clause. Existing parameterized report SQL retains explicit tenant predicates and relational database guards; it is not rewritten by an unsafe SQL parser.

`server/api.ts` handles public routes, SMS/session identity, institution slug resolution and platform/organization dispatch. Institution endpoints are mounted in `server/routes/index.ts`, which owns ordered feature routing, resource fallback and transaction idempotency. Existing students, fees, payments, reports and other modules are reused; endpoint URLs and route precedence are unchanged. Platform and service endpoints remain deliberately outside ordinary institution scope and retain their own authorization.

Verification: `pnpm typecheck`, production build, `pnpm test:refactor`, `node tests/sms-auth.mjs`. Checks exercise historical double-entry balance, provenance forgery, immutable records, descending indexing, concurrent tenant contexts, foreign IDs, partial payments/refunds, SMS identity and receipt generation.
