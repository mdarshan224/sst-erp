# Sohan Soft Tech ERP — audit and incremental upgrade

Date: 11 October 2026. Existing project retained; no replacement application, tenant reset or financial migration. Canonical customer origin: https://erp.sohansoft.in.

## Scope and evidence

Reviewed the source inventory, deployed D1 table names, six institution records and recent Worker diagnostics; traced client routing/resource caching, platform/institution permissions, session and OTP guards, schema/index/trigger definitions, institution lifecycle, staff/teaching assignments, student queries, timetable/attendance, financial posting/gateway paths, imports, domain routing and shared UI. Existing isolated Worker integration suites exercise the wider workflows. This is an engineering audit with focused fixes, not an exhaustive penetration test or certification of every line of the application.

Recent production diagnostics showed a cancelled platform dashboard request and unauthenticated session responses. These do not establish a backend crash. No authenticated real-person browser session, production financial mutation, live provider charge, SMS delivery or institution deletion was used for verification.

## Root causes and changes

| Area | Finding | Fix |
| --- | --- | --- |
| Deletion preview | Serial schema introspection/counts for every table | Two metadata queries and bounded tenant-only scalar count batches; explicitly exclude D1 internal tables |
| Deletion concurrency | Resume used a cursor read before acquiring the lease | Atomic lease acquisition returns current job state; status guard, renewed ownership and fenced row deletion |
| Recovery | A stale cursor could skip remaining operational records | Recount before advancing to objects and repair cursor to first unfinished table |
| D1 limits | A 100-row deletion needed more than 100 bound parameters | 75-row batches leave room for tenant and lease guards |
| Failure handling | Lease/error field was cleared on failure | Persist sanitized actionable error codes; hide internal lease tokens from UI and allow retries |
| Request retries | Lost quarantine response appeared as a conflicting new request | Replay the same previously authorized challenge for the same actor/name without starting another job |
| Deletion UI | Busy toggled and full preview refreshed between each batch | One ref-backed operation guard, bounded sequential run, visible progress, refresh once after completion/interruption, stop future batches on unmount |
| OTP UI | Expiry display only changed on unrelated renders | Timer updates expiry while server expiry and attempt limits remain authoritative |
| Receipt retention | Every historical document key loaded for each object page | Resolve retained receipt/certificate keys only for the current ten-object page |
| Shared data hooks | Effect forced an unnecessary loading render; same-path requester changes could expose stale results | Derived loading state, cancelled completions ignored, requester identity included in state validity |
| Institution details | Independent subscription, usage, domain and administrator requests awaited serially | Permission-preserving parallel fan-out; keyed detail component resets tenant-specific local form state |
| UI boundaries | Several client directives appeared after imports | Move directives to the actual module directive position |
| Tables | Clickable rows lacked keyboard activation; child controls could also trigger row navigation | Enter/Space activation, focus outline, interactive-descendant click protection |
| API failure UX | HTML/intermediary failures produced JSON syntax errors | Actionable invalid-response errors and retained request correlation IDs |
| Request limits | Request body was fully buffered before size check; JSON null/array reached handlers | Streaming byte limit/cancellation and object validation with structured 400/413 errors |
| Documentation | Old login/domain/billing guidance contradicted current code | Current SMS login, canonical domain and subscription-provider guidance |

No database migration was required. Existing indexes, normalized schema, immutable financial triggers, sessions, role grants, gateway settings and integrations remain in place. No new routes were added.

## Performance evidence

The isolated D1 migration/test schema contains 84 tenant tables. The old inventory algorithm requires 349 database round trips; the new query plan requires 11, a 96.8% reduction. The measured local Worker preview endpoint was approximately 30 ms on the first recorded run. Query count is derived from the executed algorithm/schema; no claim is made of a 96.8% production latency improvement. The shared hook removes one synchronous loading-state update per request effect. A 50-batch cleanup UI run performs one final full preview refresh rather than up to 50.

Existing navigation interception, 15-second bounded per-workspace GET caching, in-flight request coalescing, lazy-loaded feature modules, search debounce, server pagination and table virtualization were already present and were preserved. Bundle size and real-user p95 navigation latency have not been benchmarked on representative production devices/data. No invented speedup is reported.

## Institution audit and deletion policy

Six live institutions were read; none were edited or deleted during audit. CL-TEST and GV-TEST are the previously established test tenants and remain. GCITY-123, ASDASD, CSA-ADMY and CSA require owner review of current use before any cleanup. Names, seed provenance and suspension are not sufficient evidence to delete.

Deletion requires server permissions, exact institution name, explicit second warning, fresh session/actor/institution/action-bound OTP, five-minute expiry and five-attempt limit. Quarantine blocks tenant operations and lasts seven days. Restoration within quarantine and final purge authorization each require fresh OTP. Permanent cleanup is resumable; each batch is encrypted to R2 and read-back verified before deletion. Immutable finance/audit and their required references remain in a restricted tombstone. Shared global identities are preserved. Remote hostname disconnection is required before completion. After partial purge, recovery requires controlled operator restoration from encrypted snapshots; an automated whole-tenant restore tool is not included. Recovery key/storage must remain available and backups must have an operator retention policy.

## Deployment and remaining operational requirements

This release uses the existing Cloudflare Worker, D1 and R2 bindings. It does not provision the customer's Cloudflare account, merchant approvals, DNS or SMS credentials. Configure these using `public/setup/domain-billing-guide.md` and secure runtime settings. Never publish secrets or place them in the ZIP. Custom domain TXT/certificate records remain the exact provider-issued values. A CNAME alone cannot replace ownership validation or SSL provisioning.

Deployment rollback can restore the preceding application version because this update introduces no schema migration. Code rollback is not a recovery method for financial/operational data mutations. No production deletion has been approved or executed.
